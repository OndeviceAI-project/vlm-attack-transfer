# 02. 공통 규칙 — 두 팀이 반드시 같이 지키는 것

값은 `common/settings.py`가 기준이다. 이 문서는 그 값이 **왜** 고정인지와 확인 방법을 적는다. 둘이 다르면 settings.py가 맞고 이 문서를 고친다.

## A. 고정 조건

| 항목 | 값 | 왜 고정인가 | 확인 방법 |
|---|---|---|---|
| 질문 | "Describe this image in one sentence." | 평소 답이 짧아야 공격 효과가 보인다(천장 효과 방지). 예비 측정에서 "Describe this image."는 공격 없이도 상한까지 가는 경우가 많았다 | 결과 CSV의 text가 한 문장 답으로 시작하는지 |
| 생성 | greedy, beam 1, repetition_penalty 1.0, 샘플링 끔 | 같은 입력이면 같은 답이 나와야 재현된다. 모델 기본 generation_config는 모델마다 달라서(Qwen은 샘플링 켜짐) 명시적으로 덮어쓴다 | 같은 사진 두 번 → 같은 답 (0단계 점검) |
| 답 상한 | 512 토큰 | 예비 실험과 같다. 512 = "스스로 못 멈춤" | — |
| 종료 토큰 | 모델 generation_config의 eos_token_id **전부** | Qwen은 종료 토큰이 2개다. 하나만 보면 끝난 답을 안 끝난 것으로 센다 | 0단계 점검 출력 |
| 노이즈 상한 ε | 8/255 (L∞) | 위협 모델("사람 눈에 안 보임")의 일부. Verbose Images와 같다 | 저장된 PNG를 다시 읽어 원본과의 최대 차이 ≤ 8 |
| 사진 크기 | SmolVLM 512×512 (조각내기 끔), Qwen2-VL 448×448 | 모델 입력 크기로 **바로** 리사이즈해야 프로세서가 사진을 다시 건드리지 않는다. SmolVLM 기본 설정(longest_edge 2048)은 512 사진을 2048로 키웠다 다시 줄여서 픽셀이 평균 1.3/255, 최대 24/255 달라진다 — 노이즈 상한보다 큰 왜곡이다 | 0단계 '전처리 일치' 차이 0 |
| 리사이즈 방법 | 자르지 않고 정사각형으로 늘림, BICUBIC | 두 팀이 같은 사진 내용을 봐야 한다 | — |
| 저장 형식 | 무손실 PNG | JPEG는 공격 노이즈를 지운다 | 확장자, 파일 크기 |
| 사진 목록 | `data/image_list.csv` v1, eval 유효 30장 | 두 팀 같은 사진 | CSV의 order·coco_id |
| 기준 정밀도 | bf16 | 원본 배포 형식. 양자화 안 한 부품도 bf16 | GPU가 bf16 지원(Ampere 이상). T4는 안 됨 |
| 양자화 대상 | Linear의 weight만 | 예비 실험과 같은 정의. Conv·LayerNorm·bias·임베딩은 원본 | census: 부품별 양자화된 Linear 수 = 전체 수 |
| 가짜 양자화 | 그룹 64, 균등(min/max) 반올림, 비트 자유. **참고 구현 `common/quant_rtn.py`를 두 팀이 그대로 사용** | 비트만 바꾸고 방식은 고정. 각자 구현하면 방식이 달라진다 | 부품별 가중치 변화(%) 기록. 확인된 값: SmolVLM 비전 인코더 8비트 0.57%, 4비트 9.38% (예비 실험의 bnb nf4 9.42%와 거의 같음) |
| 실제 양자화 | bitsandbytes 8(LLM.int8) / 4(nf4), CUDA 전용 | 예비 실험과 이어지는 기준점 | census |
| 노이즈 대조군 | ±8 부호 무작위, 시드 (2026, COCO id) | 공격과 같은 크기의 '방향 없는' 노이즈 | 재생성 시 같은 파일 |
| 경우 이름 | `ref`, `rtn-V-4`, `bnb-VCLH-8` 형식 | 두 팀 결과를 한 표로 합치려면 이름이 같아야 한다 | 분석 스크립트가 이름을 해석 |

## B. 상한선

| 항목 | 상한 | 넘으면 |
|---|---|---|
| 공격 반복 수 | 기본 300, 최대 500 | 500에서 멈추고 그때까지 최선을 저장. 더 돌리지 않는다 |
| 공격 시간 (사진 1장) | SmolVLM 5분, Qwen2-VL 20분 | 그때까지 최선을 저장, 로그에 '시간 상한' 기록 |
| 1차 실험 GPU 시간 | 팀당 10시간 | 넘길 것 같으면 사진 수를 줄이지 말고 **여유분 경우(phase1-extra)를 먼저 뺀다** |
| 사진 수 | 1차 30장. 48장 넘기지 않음 | 더 필요하면 사진 목록 v2를 만들고 두 팀이 같이 바꾼다 |
| 비트 | 1차 {8,6,5,4,3} | 2비트는 여유분. 1비트 이하 없음 |
| 답 상한 | 512 | 바꾸지 않는다 |

## C. 금지

1. **평가용 사진(eval)으로 공격 설정을 고치는 것.** 조정은 dev 5장으로만. eval 사진은 공격 사진을 만들기 전에 확정한다.
2. **공식 실행 뒤 공격 사진을 다시 만드는 것.** 고정(해시 기록) 뒤에 바꿔야 하면 새 세트 이름(`adv_v2`)으로 만들고 이전 결과와 섞지 않는다.
3. **결과 CSV를 손으로 고치는 것.** 잘못됐으면 다시 실행한다. 실패한 실행은 지우지 말고 json에 사유를 적는다.
4. **설정 버전이 다른 결과를 한 표에 넣는 것.**
5. **JPEG 저장, 사진 자르기, 질문 바꾸기, 샘플링 켜기.**
6. **서로 다른 기계의 지연 시간을 비교하는 것.** 시간·에너지는 같은 실행(run) 안에서 ref 대비 비율로만 쓴다. 토큰 수가 주 지표다.
7. **공격 사진을 팀 밖으로 보내거나, 우리가 띄우지 않은 서비스·앱에 넣는 것.**

## D. 환경 요건

- GPU: bf16 지원(Ampere 이상). B팀은 Qwen2-VL-2B 공격 생성에 메모리 16GB 이상 권장. Colab 무료 T4는 bf16이 안 돼 공식 실험에 쓰지 않는다.
- 패키지: torch 2.x, transformers 5.x, bitsandbytes 0.50 이상(bnb 경우), pillow 11.x. **정확한 버전은 실행마다 json에 자동 기록**되게 한다. 두 팀의 주 버전(major)이 같아야 한다.
- 한 실행(run) 안에서 `ref`와 모든 경우를 **같은 기계, 같은 세션 조건**으로 돌린다. 다른 실행의 ref를 빌려 쓰지 않는다.
- 공격 생성에 쓴 기계와 평가에 쓴 기계가 달라도 된다(공격 사진은 PNG로 고정되므로). 어디서 만들었는지는 로그에 남긴다.

## E. 공식 실험 전 체크리스트 (0단계)

각 팀이 공식 실험 전에 한 번, 환경이 바뀌면 다시 돌리고 결과를 실험기록 이슈에 붙인다.

- [ ] 전처리 일치: 공격 코드가 만드는 pixel_values와 프로세서가 같은 사진으로 만드는 pixel_values의 차이 최댓값 = 0 (1e-4 미만)
- [ ] 부품 나누기: 모델의 모든 Linear가 V/C/L/H 중 정확히 하나에 속함 (어디에도 안 속하는 층이 있으면 PARTS 수정)
- [ ] 종료 토큰 목록 출력, 질문 템플릿 출력(Qwen은 시스템 문장이 자동으로 붙는지 확인)
- [ ] 재현성: 같은 사진을 두 번 넣어 토큰 수와 문장이 같음
- [ ] bf16 지원, 사용 가능한 메모리, bnb 가능 여부, 에너지 측정 가능 여부
- [ ] `settings.SETTINGS_VERSION`이 두 팀 모두 같은 값

## F. 기록 의무

실행(run) 하나마다 다음이 남아야 한다. 없으면 공식 결과로 치지 않는다.

- `results/<모델>/<실행ID>.csv` — 답 하나가 한 줄(열 정의 docs/05)
- `results/<모델>/<실행ID>.json` — 설정 버전, 설정 전체 스냅샷, 환경(GPU·버전·git 커밋), 경우별 census와 가중치 변화, 실행 명령, 시작·끝 시각, 건너뛴 경우
- 실험기록 이슈(`.github/ISSUE_TEMPLATE/실험기록.md`) 1개 — 무엇을, 어떤 사유로, 결과 요약, 이상한 점
- 실행 ID 형식: `YYYYMMDD-HHMMSS_<모델>_<묶음이름>`

## G. 설정을 바꾸는 절차

1. 바꾸려는 사람이 이슈를 연다: 무엇을, 왜, 이미 나온 결과에 미치는 영향.
2. 두 팀 각 1명 이상 동의.
3. `common/settings.py`의 값과 `SETTINGS_VERSION`을 올리고, docs/02의 표를 고치는 PR 하나로 올린다.
4. 이전 버전 결과는 `results/`에 그대로 두되 분석에서는 섞지 않는다.

## H. Git 협업

- 브랜치: `a/<내용>`, `b/<내용>`, `docs/<내용>`. `main`에 직접 커밋하지 않는다.
- 커밋 메시지: `[A] 공격 사진 30장 생성 로그` 처럼 팀 표시 + 내용. 결과를 올리는 커밋은 실험기록 이슈 번호를 적는다(`#12`).
- PR 하나 = 실행 하나 또는 문서 변경 하나. 결과 PR은 **다른 팀** 1명이 체크리스트(PR 템플릿)를 보고 승인한다.
- 커밋하는 것: 코드, 문서, `data/image_list.csv`, 모델별 `data/sets/*` PNG(세트당 수십 MB), 결과 CSV·JSON, 보고서 표·그림.
- 커밋하지 않는 것: 내려받은 COCO 원본(`data/coco_cache/`), 모델 가중치, 가상환경, 노트북 체크포인트, 임시 파일. `.gitignore`에 있다.
- 노트북은 결과 셀을 지우고 올린다(큰 출력 방지). 결과는 CSV로 남는다.

## I. 하나만 두는 코드

두 팀이 각자 짜면 같은 규칙을 지켜도 숫자가 달라질 수 있는 코드는 하나만 두고 같이 쓴다.

- 공통 값: `common/settings.py`
- 가짜 양자화·census: `common/quant_rtn.py`
- 공격 사진: `notebooks/A_smolvlm/attack_smolvlm.py` (B팀은 docs/07의 항목만 바꾼 복사본)
- 4단계 분석(지표·신뢰구간·그림): 공동 담당 1명이 하나만 만들고, 두 팀 CSV를 모두 이 코드로 계산한다. 팀별로 따로 계산한 숫자는 발표·보고서에 쓰지 않는다.
- 3단계 평가 코드는 팀마다 노트북이 다르지만, 생성 설정(`GEN_KWARGS`)·결과 열(docs/05)·census를 그대로 따르고 상대 팀이 PR에서 확인한다.

## J. 윤리

- 공격 사진은 공개 모델을 **우리 기기에서** 돌릴 때만 넣는다.
- 공개 데이터(COCO val2017)와 공개 모델만 쓴다.
- 보고서에는 결과와 함께 **대가**(품질·용량)와 **한계**를 같은 비중으로 적는다. 공격만 보여 주는 결과물이 되지 않게 한다.
